# Як я покращив життя за допомогою AI: Photo Tagger

## 0. План рішення

| Поле | Значення |
|---|---|
| Проблема | У людей сотні фото (телефон, скріншоти, скани), які неможливо знайти за змістом: назви `IMG_2231.jpg`. Пошук потрібен кілька разів на тиждень |
| Поточний процес | Гортати галерею вручну, ~3-5 хв на пошук одного фото. Підписати 100 фото вручну: ~40 хв (оцінка: ~25 с на фото) |
| Дані | Зображення jpg/png/webp з телефону та скріншоти |
| Рівень рішення | 1 (prompt + локальна vision-модель): одного запиту на фото достатньо, зовнішні дані не потрібні |
| Метрика + ціль | Активний час людини на 100 фото: ~40 хв → ≤5 хв. Якість тегів: ≥80% доречних. Пошук фото: 3-5 хв → ≤20 с |
| Ризики / fallback | Неправильний опис, помилки в українській, невалідний JSON → перевірка вибірки вручну, `--force` для переопису, помилки логуються |

## Архітектура

```
Інтерфейс: командний рядок (photo_tagger.py) і вікно на tkinter (photo_gui.py)
папка з фото → Pillow (зменшення, EXIF) → Ollama (gemma3:4b) → JSON (опис, теги, категорія)
            → index.json → search (пошук за словами) → список файлів
                         → evidence/runs.csv (лог часу)
```

Команди: `describe <папка>` (індексація), `search "запит" [--all]` (пошук), `stats` (статистика).

## Використані технології

Ollama, gemma3:4b (vision), Python, Pillow, бібліотека `ollama`, PyCharm, Windows.

## Обґрунтування рівня

Один запит із зображенням дає потрібний результат, інструменти чи зовнішні дані не потрібні (рівень 1). RAG або агент були б надлишковими. Fine-tuning не потрібен: для пошуку по фото достатньо загальних описів. Розглянуті альтернативи: ручне підписування, хмарні сервіси (Google Photos, платні API), CLIP-ембедінги.

## Ризики

| Ризик | Ймовірність / критичність | Що робити |
|---|---|---|
| Модель вигадує деталі на фото (в тестах так і було) | Висока / низька | Перевіряю вибірку вручну, `--force` для переопису |
| Російські слова або суржик в українських описах (траплялося: «Кот») | Середня / низька | Перевірка вибірки, ручна правка в `index.json` |
| Невалідний JSON від моделі | Низька | `format="json"`, помилка логується, фото пропускається |
| Слабке залізо, повільна обробка (в тестах ~70 с на фото) | Висока / середня | Запускати обробку у фоні, зменшення фото до 1024 px, кеш за хешем (оброблене не повторюється) |
| Незвичні фото (темні, розмиті, скани) | Середня / низька | Категорія «інше», ручна правка в `index.json` |
| Формат HEIC не читається | Висока / низька | Конвертація в JPG |
| Кодування консолі Windows ламає українські запити («к?т») | Висока / низька | `chcp 65001` і `PYTHONUTF8=1` |

## Відповіді на питання з п.8

1. **Яку проблему ви вирішували?** Фото в галереї мають безглузді назви (`IMG_2231.jpg`, `photo_2025-09-20_...jpg`), тому знайти потрібне можна тільки гортанням. Я зробив інструмент, який описує фото текстом і дає пошук за словами.

2. **Чому ця проблема реальна та корисна для автоматизації?** Фото накопичуються постійно, а пошук потрібен регулярно: скріншот конспекту, фото документа, картинка з поїздки. Підписувати вручну ніхто не буде, бо це нудно й довго. Задача однотипна (одне фото → один опис), тому добре підходить для AI.

3. **Як задача виконувалась до AI?** Вручну гортати галерею (3-5 хв на пошук одного фото) або взагалі не підписувати. Якби підписувати, це приблизно 25 с на фото, тобто ~40 хв на 100 фото.

4. **Яке AI-рішення ви побудували?** Python-скрипт `photo_tagger.py`. Він зменшує фото до 1024 px, відправляє у vision-модель через Ollama і отримує JSON з описом, тегами, категорією та ознакою тексту. Результат зберігається в `index.json`, оброблені фото пропускаються за хешем. Пошук працює за словами запиту (з грубим стемінгом для української) у режимах «будь-яке слово» та «усі слова» (`--all`). Кожен прогін логується в `evidence/runs.csv`.

5. **Чому ви обрали саме цей рівень AI-рішення?** Для кожного фото достатньо одного запиту, дані лежать на самому фото, ланцюжок кроків не потрібен. Тому рівень 1. RAG додав би складність без користі, fine-tuning не виправдав би себе без сотень власних прикладів.

6. **Які альтернативи ви розглядали?** Ручне підписування (довго), хмарні сервіси на кшталт Google Photos (приватність, залежність від сервісу), платні API (вартість), CLIP-ембедінги для семантичного пошуку (складніше, не потрібні описи), більша модель `qwen2.5vl:7b` (кращі описи, але потребує більше пам'яті).

7. **Які AI-моделі та інструменти ви використали?** `gemma3:4b` через Ollama, Python, Pillow (підготовка зображень), бібліотека `ollama`, PyCharm.

8. **Які проблеми або помилки виникли?**
   - Модель вигадує деталі: «жест rock on» і «зібраність» для кота, «пагорб» і «пісок» для фото собаки в місті.
   - В одному описі з'явилося російське слово «Кот».
   - Повільна обробка: ~70 с на фото на моєму ноутбуці.
   - Українські запити в консолі Windows ламалися («к?т»), що вирішилося через UTF-8.
   - Початкова версія пошуку показувала «збігів: 1» для кожного фото й не мала режиму «усі слова», тому я додав `--all` і виведення збіглих слів.

9. **Наскільки надійним є ваше рішення?** Головний об'єкт фото модель визначає правильно (3 з 3), тож для пошуку («кіт», «собака») рішення працює. Але деталі та теги ненадійні: приблизно 30% тегів були недоречними. Для пошуку це терпимо (зайвий результат не критичний), але автоматично перейменовувати файли чи довіряти описам без перевірки не варто. Вибірка з 3 фото мала, тому ці цифри орієнтовні.

10. **Що змінилося після впровадження AI?** З'явився текстовий пошук по фото, який займає менше секунди замість кількох хвилин гортання. Людині більше не треба вручну підписувати кожне фото: достатньо запустити команду й вибірково перевірити результат.

11. **Скільки часу або інших ресурсів вдалося заощадити?** Активний час людини на 100 фото скоротився з ~40 хв до ~5 хв (~87%). Але є важлива оговорка: машинний час становить ~2 години на 100 фото, і ціль «≤10 хв» не досягнута. Це прийнятно лише тому, що обробка йде у фоні (наприклад, вночі). На комп'ютері з GPU вона була б у рази швидшою. Грошових витрат немає.

12. **Що б ви змінили, якби продовжували розвивати рішення?** По-перше, посилив би промпт (до 5 тегів, лише видиме, без російських слів) і порівняв `gemma3:4b` із `qwen2.5vl:7b`. По-друге, додав би автоперейменування файлів за змістом. По-третє, зробив би веб-інтерфейс з мініатюрами та пошук через ембедінги, щоб запит «тварина» знаходив і кота, і собаку. Також додав би підтримку HEIC.
